# Backend

The storefront stays a static site. Alongside it sit twelve functions, a
Postgres database and Razorpay. Nothing about the build changed: `dist/` is
still generated by `node build.mjs` and still deploys as files.

```
dist/                        the site, as before

api/checkout.js              price a cart, open a Razorpay order, record ours
api/razorpay-webhook.js      the only thing that marks an order paid
api/stock.js                 live quantities for the shop
api/contact.js               store a contact message, notify us
api/newsletter.js            record a subscriber

api/auth/register.js         create an account, sign in
api/auth/session.js          GET who am I · POST sign in · DELETE sign out
api/auth/account.js          profile · address · password
api/auth/recover.js          request a reset link · spend one

api/admin/orders.js          list · resolve · thank · ship · sync to a sheet
api/admin/messages.js        list · mark handled
api/admin/stock.js           list · set a quantity

api/_lib/                    pricing, database, email, Razorpay, plumbing
db/schema.sql                ten tables
db/seed-stock.mjs            fill the stock table from the catalogue
```

**That is 12 of 12 Serverless Functions on Vercel's Hobby plan.** Several
handlers take an `action` in the body rather than existing as separate files
for exactly this reason. Anything new shares one of them, or the project
moves to Pro or to Railway.

Other scripts, none of which deploy:

```
npm run db:setup    apply db/schema.sql
npm run db:check    what is configured, what is missing, what is owed
npm run smoke       exercise the database paths against a real database
npm run db:export   a copy of everything, into backups/<timestamp>/
npm run demo        realistic test orders · --remove to clear them
```

## The one rule

**The browser is never believed about money.** It sends product, size and
quantity. Prices come from `src/data.mjs`, stock from the database, shipping
from the rule in `api/_lib/pricing.mjs`, and the total is computed on the
server every time. A cart that claims lavender costs ₹1 is charged ₹699.
There is a test for exactly this.

Money is integer paise everywhere — in the code, in the database, and in what
Razorpay is told. Rupees as decimals round badly, and these are real charges.

## What settles an order

A browser returning from the payment screen proves nothing: it can close, or
lie. Orders become `paid` only in the webhook, which is signed by Razorpay and
verified against the raw request bytes.

The webhook is built to be delivered twice, because Razorpay retries. Only an
order still at `created` moves, so a repeat delivery changes nothing and
stock cannot be decremented twice.

There is deliberately no verifier for the handshake the browser hands back
after payment. One existed and was never called: it proves a response was not
forged in transit, never that money moved, and leaving it there invited a
later caller to mistake it for proof of payment.

## Setup

1. **Database.** Create a Postgres database (Neon's free tier is enough), then:

   ```bash
   npm run db:setup
   npm run seed
   npm run db:check
   ```

   `db:setup` applies `db/schema.sql` over the Neon driver, so it needs no
   `psql` installed. `db:check` reads the same schema file to decide what
   should be there, so the two cannot drift apart the way they did once.

2. **Razorpay.** Sign up, stay in **Test mode**, and take the key id and
   secret from Settings → API Keys.

3. **Environment.** `cp .env.example .env.local` and fill it in. Never commit
   it; `.env*` is already gitignored.

4. **Webhook.** Settings → Webhooks → add
   `https://<your-domain>/api/razorpay-webhook`, subscribe to
   `payment.captured` and `payment.failed`, and set the secret to the same
   string as `RAZORPAY_WEBHOOK_SECRET`.

   A webhook cannot reach `localhost`. To test locally, tunnel (`ngrok http
   3000`) and point the webhook at the tunnel.

5. **Deploy.** Vercel, importing the repo. `vercel.json` already declares the
   build and the functions. Add the same environment variables there.

## Testing payments

In test mode, card `4111 1111 1111 1111`, any future expiry, any CVV. No money
moves. Verify an order reaches `paid` and that stock went down:

```sql
select id, status, total_paise, created_at from orders order by created_at desc limit 5;
select sku, quantity from stock where quantity < 10;
```

## Accounts

**Ordering requires an account.** Browsing, searching and filling a cart do
not — the gate is at checkout and nowhere earlier.

`api/checkout.js` refuses a request without a session, and that refusal is the
rule. The checkout page hiding its form from a logged-out visitor is only
courtesy, so they are not left filling in an address they cannot submit.

The known cost: some first-time buyers leave rather than register. It buys a
customer record against every order, an order history, and one address on
file. `orders.customer_id` stays nullable, because orders placed before this
rule existed are not invalid.

```
api/auth/register.js   create an account, sign in
api/auth/session.js    GET  who is signed in, and their past orders
                       POST sign in
                       DELETE sign out: delete the session, clear the cookie
api/auth/account.js    change the profile, the address, or the password
api/auth/recover.js    request a reset link, and spend one
```

Signing in, signing out and asking who you are were three files once. They
are one now, because they are three verbs on a single thing — the session —
and because a function slot is a scarce resource here.

Pages: `/account/register/`, `/account/login/`, `/account/forgot/`,
`/account/reset/`, `/account/` — all noindex, and
the sitemap now excludes anything noindex rather than skipping a hardcoded
list, so they cannot drift back into it.

### Where the data lives

The same Postgres database as orders, in two new tables.

| Table | Holds |
| --- | --- |
| `customers` | email, name, optional phone, scrypt password hash, lockout counters |
| `sessions` | SHA-256 of the session token, its customer, its expiry |

Two things are deliberately *not* stored:

- **The password.** Only a scrypt hash with a random per-password salt. If the
  database is ever copied, the attacker has hashes that cost real money to
  attack one at a time, not a list of credentials to try on everyone's email.
- **The session token.** The browser holds the token; we hold its SHA-256. A
  leaked `sessions` table therefore cannot be used to sign in as anyone.

The token travels in a cookie that is `HttpOnly` (script cannot read it, so an
XSS bug cannot steal it), `Secure` (never sent over plain http) and
`SameSite=Lax` (not attached to cross-site POSTs, which is what makes CSRF
against these endpoints a non-event).

Nothing about an account is stored in the browser beyond that cookie. The cart
remains in `localStorage` and is not tied to an account — logging in on another
device does not bring your cart with you.

## Messages and subscribers

```
api/contact.js      store a contact message
api/newsletter.js   record a subscriber
```

Both forms previously told the visitor their message had been sent and then
discarded it. The newsletter one went further and promised a 10% code that
nothing could send.

Read what has come in:

```sql
select name, email, subject, created_at from messages
 where handled_at is null order by created_at;

select count(*) from subscribers where unsubscribed_at is null;
```

Both endpoints carry a honeypot field named `website`: hidden off-screen,
untabbable and hidden from screen readers, so a person never meets it. A
submission with it filled in gets a cheerful 200 and is dropped, because
telling a bot it failed only invites a better-dressed attempt.

Neither sends email, so nobody is notified that a message arrived. Until
that exists, check the table.

## Discount codes

`discount_codes` holds them; `src/discount.mjs` holds the rules and is tested
without a database. A code is either a whole percentage or a fixed number of
paise, with an optional minimum spend, usage limit and expiry.

Four decisions worth knowing before changing any of it:

- **Shipping is never discounted**, and the free-shipping threshold is judged
  on the subtotal *before* the code. A ₹1,050 cart with a 20% code keeps its
  free shipping rather than dropping under the line and gaining a ₹79 charge.
- **Percentages round to the nearest whole rupee.** Every price in the shop
  is a whole number of rupees; 10% of ₹699 is ₹69.90, which renders as
  "₹69.9" and looks like a bug to the person about to pay.
- **A code can never take the payable total below ₹1** — Razorpay's floor and
  the schema's `total_paise > 0`. It is capped, not refused.
- **A code counts as used when the webhook settles the payment**, not when a
  checkout starts, so abandoned carts do not burn a limited run. The cost is
  a window in which concurrent checkouts can overspend the limit by the
  number of them open at once.

`POST /api/checkout` with `{ preview: true }` prices a cart and stops —
no order row, no Razorpay call. That is how the checkout page shows what a
code is worth, and it means the quote and the charge come from one path.

Codes are made and retired from the Codes tab in `/admin/`, through actions
on `/api/admin/orders` rather than a file of their own — see the note at the
top of that handler about the twelve-function cap. A code cannot be edited
once it exists; retire it and issue another, because editing one silently
changes what it is worth to everyone already holding it.

## Saved addresses

Checkout writes the delivery address back to the account, and `/api/auth/session`
returns it so the next checkout is prefilled. One address per customer,
overwritten each time: a chooser is worth building when someone asks for one.

## Admin

`/admin/` — orders, messages, stock and discount codes. Noindex and out of the sitemap.

```
api/admin/orders.js     list; mark dispatched; record what was done about an
                        oversold order; send a thank-you; download a CSV or
                        push rows to a Google Sheet
api/admin/messages.js   list; mark a message handled
api/admin/stock.js      list; set a quantity
```

The sheet export lives inside `orders.js` rather than beside it because
adding a thirteenth function silently broke every deployment once. The cap
is not a warning you get; it is a build that stops.

There are no separate admin accounts. `customers.is_admin` is a flag on an
ordinary account, so there is one identity, one login and one session
mechanism to get right rather than two.

```bash
npm run admin -- you@example.com            # after registering on the site
npm run admin -- them@example.com --revoke
```

The account has to exist first: the person registers at
`/account/register/` themselves, and only then does this find them. There is
no way to create someone else's account, which is deliberate — it would mean
choosing their password for them.

Granting admin is a command against the database, never a button. A "make
this person an admin" control is the one whose compromise hands over
everything, and it is not needed often enough to be worth having.

Every endpoint calls `requireAdmin` and checks the flag **in the database on
each request**, so revoking takes effect on the next request rather than
whenever the session expires. A signed-in non-admin gets the same **404** as
a stranger: a 403 would confirm that `/api/admin/*` exists and is worth
attacking.

Stock is set outright rather than adjusted by a delta — counting the shelf
and typing that number is what actually happens, and working out the
difference first is a step at which people make mistakes.

**Marking an order dispatched emails the customer**, with the tracking
reference if one was typed. The order is marked `shipped` first and the send
is attempted after, because a failed email must not un-dispatch an order that
has physically left. The page reports which of the two happened rather than
claiming the customer was told when they were not — and like everything else
here, nothing is actually sent until email is configured.

## Known trade-offs

**Stock is not reserved between checkout and payment.** Two shoppers can both
pass the stock check on the last bottle; the second to pay is caught by the
`quantity >= qty` guard and their order is marked `oversold` rather than
silently shipped. That is deliberate: reserving stock at checkout would let
abandoned carts hold inventory hostage, which at this volume is the more
common and more costly failure. If orders start colliding, add a reservation
with an expiry.

**The shipping fee is a placeholder, not a decision.** `site.shippingFlat`
is ₹79 below the ₹999 free-shipping threshold. The FAQ, the shipping policy,
the cart drawer and `priceCart()` all now say the same thing — they disagreed
once, and the FAQ claimed charges were "calculated at checkout based on your
location" while the code charged a flat fee anywhere — but what they agree on
has still never been chosen by anyone.

**"Sign out everywhere" is the password change.** Changing a password from
`/account/` ends every other session and keeps the current browser's. There
is no separate button for it, because the case that matters — you think
someone has your session — is the case where you want a new password too.

**Order confirmation is sent.** `markPaid()` emails the customer the moment
payment settles — reference, line items with line totals, subtotal, shipping,
total and the delivery address, read from `order_items` as recorded at the
time of sale.

It is sent once: the send is claimed with a conditional update
(`confirmed_email_at is null`) that only one caller can win, and the claim is
released if the provider refuses, so a null column genuinely means "this
customer is still owed one". `npm run db:check` reports any that are. An
oversold order is deliberately **not** sent one — that customer needs a
person. An email failure never stops the webhook answering 200, because a
non-2xx asks Razorpay to redeliver the whole event.

**The contact form notifies you.** `api/contact.js` emails `EMAIL_REPLY_TO`
(or `EMAIL_FROM`) when a message arrives, with reply-to set to the sender so
answering it answers them. The message is stored first and the 201 is
returned either way: a visitor is never told their message failed because our
own notification did.

Neither sends anything until `EMAIL_PROVIDER`, `EMAIL_API_KEY` and
`EMAIL_FROM` are set. Until then both log the reason and carry on, and the
admin page says email is not configured rather than failing on click.

**Nothing has been delivered by a real provider yet.** The paths are covered
by `npm run smoke` against a real database with an injected sender, which is
not the same as an inbox receiving one.

## Before taking real money

These are not optional, and two of them are legal requirements in India:

- **Policy pages — written, but not finished.** `/privacy/`, `/terms/`,
  `/refunds/` and `/shipping/` exist, are linked from the footer and from
  checkout, and are in the sitemap. They carry **23 visible `TODO` blocks**
  for facts nobody has stated yet: legal entity, GST status, returns window,
  whether opened bottles come back, refund timeline, courier, grievance
  officer. Each renders on the page in a yellow box, so publishing them
  unfinished is hard to do by accident. Search `src/policies.mjs` for
  `"todo"`. Until those are answered the pages will not satisfy Razorpay and
  should not be treated as a legal position.
- **Business verification.** Razorpay needs PAN, bank account and, above a
  threshold, GST registration.
- **Switch the keys.** `rzp_test_…` to `rzp_live_…`, and a fresh webhook
  secret. `npm run db:check` then reports which mode the keys are in, and
  warns when real cards are live.
- **Confirm the shipping fee.** `site.shippingFlat` is set to ₹79 below the
  ₹999 free-shipping threshold. That number was chosen as a placeholder — the
  site had never stated a fee — and should be a decision, not an inheritance.

**Password reset exists.** `/account/forgot/` asks for a link,
`/api/auth/recover` mints one, and `/account/reset/` spends it. The token is
32 random bytes and only its SHA-256 is stored — a reset token *is* the
account for the hour it lives, so it gets the same treatment as a session.

Single use, one hour, three requests per address per hour. A successful reset
ends **every** session for that customer and burns any other outstanding
links, because someone resetting a password sometimes cannot get in
*because somebody else can*.

The request step answers the same whether or not the address has an account.
It refuses up front when email is not configured, rather than saying a link
is on its way and sending nothing — that is a fact about the shop, not about
the address, so saying it reveals nothing.

**No link can actually be sent until email is configured.** The flow is
proven against a real database with tokens minted directly; no reset email
has reached an inbox.

**`api/` is now full: 12 of 12 Serverless Functions.** Anything new has to
share an existing handler, as `/api/auth/recover` and `/api/admin/orders`
already do, or the project moves to Pro or to Railway.

**No unsubscribe endpoint.** Every newsletter signup generates and stores an
`unsubscribe_token` and nothing consumes it, so there is no way off the list.
Harmless while nothing is sent to subscribers; a compliance problem the
moment a marketing email goes out. This has to exist **before** the first
one, not after.

**Email addresses are not verified.** Anyone can register with an address they
do not own. That matters more once email is being sent to it.

**Login lockout is per account, not per IP.** Ten failures locks that email for
fifteen minutes, which also means someone can deliberately lock out an address
they know. The real fix is rate limiting at the edge, by IP.

**The checkout flow is unproven end to end.** The gate, the order summary and
the prefill were checked in a browser against a stubbed `/api/auth/session`. What
has never run is the real sequence: a session cookie from Postgres, a
Razorpay order, their payment screen, and the webhook settling it. That needs
credentials and a database.
